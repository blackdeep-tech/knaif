# knaif 1.3 — per-skill adapters, the superskill, and more skills

**Status:** Draft — scope only, design to be discussed · **Created:** 2026-09-27 · **Completed:** —
**Owner:** owner + core + training · **Ref:** follows [release-1.2](2026-09-25-release-1.2.md); evidence
from [policy-gate-and-skill-adapters](2026-09-26-policy-gate-and-skill-adapters.md)

**Goal:** Scale knaif past two skills without one skill's training regressing another, and route a
request to the right skill before planning.

## Why

Release 1.2's three union retrains (sft-v6/v7/v8) all failed on the one decision every skill shares
(plan / clarify / reject), and edits to one skill leaked into the other through it
(`evals/runs/2026-09-26_r5a-*`). With N skills every data change is an N-way regression risk and
every candidate costs N full evals.

## Scope (to be designed; nothing decided beyond this list)

- [ ] **Superskill / router** — owner wants to discuss the design first: how a request is routed to
      a skill (retrieval, a small classifier, the model itself), what happens across skills
      (a request touching two), and how the router is evaluated.
- [ ] **Per-skill LoRA adapters on a shared base** (E2b of the experiment plan, restated):
      - entry question: does base + adapter **as served** (quantized base, f16 adapter at load) meet
        each skill's acceptance bar? Not byte parity with a merged model (E2a showed why: the Q4 gap
        is quantization order; f16 is near-exact);
      - shared core-control rows in every adapter; isolation check (retrain one adapter, the other
        skill's scores byte-identical);
      - native: `llama-cpp-2` 0.1.150 already exposes `lora_adapter_init/set/remove`; the CLI needs
        per-request adapter selection; `convert_lora_to_gguf.py` pinned to the build's llama.cpp tag.
- [ ] **New skills**, each trained as its own adapter against its own bar.
- [ ] **Safety stays structural** (E1/E1b: a request-text gate does not generalize). Decide whether
      the safety bar measures refusal wording or "nothing unsafe executes".

## Already in place from 1.2

- Python eval lane: `lora_path` in an `eval_backends.yaml` stanza applies an adapter at load
  (`orchestrator.py`, `test_orchestrator.py::test_lora_path_*`).
- Measured on 2026-09-26: 4B adapter 66.1 MB GGUF, load 25 ms, attach 28 ms
  (`evals/runs/2026-09-26_e2a-lora-spike_success`).
- A 40-row fresh probe frozen for independent confirmation
  (`evals/runs/2026-09-26_r5a-v8-candidates_success/probe_*.jsonl`), plus sft-v4's and v1-1.7b's
  probe scores as references.
- The R3/R5a ffmpeg rows held back from training (`scripts/gen_train.py`,
  `ffmpeg_rows_held_back`): a starting point for balanced per-skill data, not trained as-is.
