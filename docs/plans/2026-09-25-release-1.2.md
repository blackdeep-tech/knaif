**Goal:** Ship knaif 1.2.0 and the retrained 4B and 1.7B models as one release, merged to `main`
from a single release branch, with every shipped path — CUDA, Vulkan and the CPU fallback —
accepted on the binary.

## Why the order changed

Until 2026-09-25 the plan was to publish `sft-v4` as `knaif-qwen3-4b-v2` on its own. The owner
revised it:

- **No partial models on HF.** A public model number is only used when something is published, so
  skipping `sft-v4` leaves no gap: the next published 4B is still `-v2`.
- **Models and knaif go together.** A model is published inside a knaif release, never alone.
- **There is no 1.7B v2**, and the published 1.7B v1 fails the safety gate (10/11,
  `ffmpeg_safety_system_root_dir`). A release that still recommends it would ship a known safety
  failure.
- **CPU is the main fallback, not an option.** The release artifact is the `vulkan` kind, which
  carries the same llama.cpp CPU backend and uses it on any machine without a usable GPU
  (NATIVE.md §5.3). The 2026-09-25 cross-backend check
  ([report](../../evals/runs/2026-09-25_backend-parity-v2_plans/report.md)) left CPU ffmpeg over
  its flip bound (37/851 decisions vs CUDA), so that path has to be accepted too.
- **Try training before accepting the backend gap.** The same ~5% of utterances flip under every
  perturbation (24 of the 35 compute-config flips are among the 44 backend flips): the model is on a
  near-tie there, and training can widen it. llama.cpp does not make backends agree bit-for-bit
  and has no setting that does (maintainer: "there isn't currently a way").

## R0 — Decisions (2026-09-25)

- [x] **knaif version: 1.2.0**, not 2.0.0. Measured against the `v1.1.0` tag: no CLI subcommand
      or flag removed or renamed (one additive flag: `backend list --json`), no change to the Python SDK's
      public API, the model manifest only gains an entry, and `knaif-qwen3-4b-v1` still runs
      correctly under the current code (ffmpeg 0.9189 in the 2026-09-24 v2 verdict). The changes are
      behavioural and belong in the release notes:
      - out-of-scope requests now `clarify` ("this skill can't do that") instead of `reject`;
        `reject` is reserved for safety-policy violations;
      - every step of a multi-step plan runs (1.1.0 ran only the first);
      - a derived output name never overwrites an existing file; edits keep the input's container;
      - a CUDA payload installed for 1.1.0 is refused by 1.2.0 and must be re-installed. This is by
        design (`knaif_version` in the backend manifest) and has been true of every release.
- [x] **Model numbers stay their own line: `knaif-qwen3-4b-v2`, `knaif-qwen3-1.7b-v2`**, not tied
      to knaif's number and not `v1.1`. Reasons:
      - knaif 1.2.1 or a macOS follow-up would ship the same models, and a model-per-knaif-major rule
        would force knaif 3.0 for the next model even with nothing broken;
      - the manifest's rule is +1 per publication, and a minor number would promise "same behaviour,
        fixes only", which a retrained model cannot;
      - the store keys on the model's filename, which is what makes a knaif upgrade with an unchanged
        model re-download nothing.

      The binding is made **explicit** instead: a `released_with:` field per manifest entry, the
      release notes, and a knaif ↔ model table on the HF card (R6).
- [x] **The 1.7B is retrained in the same cycle**, on its own bar. Safety stays at 100%. The
      quality floors may be lower than the 4B's, but they are written into the skills' acceptance
      bars **before** the model is measured, never fitted to its result.
- [x] **The 4-hour CPU L4 runs on the release candidate, not on `sft-v4`.** `sft-v4` will not ship, so
      its CPU score would decide nothing. The "before" baseline for "did training close the backend
      gap" is the plan-level flip count already measured (CUDA vs CPU 37, vs Vulkan 29 on ffmpeg).
- [x] **macOS is not a blocker.** `contracts/release/platforms.yaml` already lists `macos` as
      `status: planned`. If it misses 1.2.0 it ships in 1.2.x, with the same models, and only the
      binary is postponed. Shared-code fixes from `feat/macos-support` (the OpenSSL guard, the
      llama-cpp-2 `openmp` feature) should still reach `release/1.2.0` if they are ready, since they
      change what every platform builds.

- [x] **L3's bar: zero port bugs, plus bounded plan disagreement** (owner, 2026-09-25). The 1.0 rate
      bar is unreachable by construction: the runtimes link different llama.cpp builds, and even
      three native backends do not agree 100%. L3 now fails on any utterance where both runtimes chose
      the same plan but rendered different commands (a porting defect, must be 0). Plan-level
      disagreement must stay within a bound written before the run, as in the 2026-09-25 backend check.
      Closes the open owner decision in [skill-quality-lifecycle](2026-09-10-skill-quality-lifecycle.md)
      (L3a) and unblocks `supported`, the only release-eligible status.
- [x] **PDFium is bundled in 1.2.0** (owner, 2026-09-25): 6.92 MB beside the binary in every
      artifact, per the 2026-07-05 decision. The download-on-demand tier of
      [skill-payloads](2026-09-21-skill-payloads.md) stays a later plan.
- [x] **Daemon and prompt-cache reuse move to 1.3.0** (owner, 2026-09-25). Reusing the cache between
      requests is what config parity switched off, because results depended on the previous request;
      bringing it back would invalidate the measurements this release rests on.
- [x] **Documents grading is strengthened before training** (owner, 2026-09-25). Fix it, re-measure
      `sft-v4` with it as the new baseline, then train (R3a).

- [ ] **Merge policy (owner, 2026-09-25).** Release and big feature branches merge into `main` with a

      creates new commits git cannot match to the originals, so their later merge conflicts and
      duplicates history. It also keeps every commit an eval report cites reachable from `main`. Read
      `main` one entry per PR with `git log --first-parent main`. A release branch takes in `main`'s
      changes by merging, never rebasing. Repo settings to change (owner): in the `main-guardrails`
      ruleset untick **Require linear history** and add **Merge** to the allowed merge methods; in
      Settings → General tick **Allow merge commits**. Everything else in the ruleset stays.
