## Decisions

- 2026-10-26 — 1.4.0 ships no new model: it serves the published `knaif-qwen3-4b-v2` and
  `knaif-qwen3-1.7b-v2` (owner).
- 2026-10-27 — toolchain refreshed (`chore/deps-1.4.0`): Rust 1.96.0 → 1.99.1; `llama-cpp-2` /
  `llama-cpp-sys-2` 0.1.150 → 0.1.160, which bundles llama.cpp `d812350` (2026-10-05; was
  `9e3b928`, 2026-06-07). Checked on Windows: CPU, Vulkan and CUDA build, both GPU kinds offload
  37/37 layers, and `just parity <skill> --limit 20` on CUDA is 20/20 for both skills.
- 2026-10-28 — the feature rows join the gates (owner): each skill's `eval_url`, `eval_alert` and
  `eval_batch` rows are appended to its `eval.jsonl` (ffmpeg +42, documents +25) and the separate
  files removed, so acceptance, the snapshot, the release subset and the native evidence all
  measure them. Their review tags are `url_input`, `alerts_and_folders` and `many_files`; the
  existing capability tags they carried are removed (as `hard2`'s rows carry none), `clarify` is
  kept on the rows that expect it. Their floors are written from the re-lock that first measures
  them. `corpus-check` fixes on the way in: four `expected_tool` placeholders.
- 2026-10-28 — kept rows `ffmpeg_204` and `ffmpeg_208` fixed (owner, G2.1 exception): they
  expected `clarify` for "split clip.mp4 into 2-second segments" and "grab every 10th frame",
  which `split_video` and `extract_frames` now do. Each keeps its first utterance; the vague second
  one ("chop clip.mp4 into multiple clips", "extract frames at 1 frame per second") is replaced by
  a precise wording, the row expects a plan graded on the `one_long/` fixture's files (38 parts;
  188 stills, both run for real), `unsupported` is dropped, and both are re-pinned.
- 2026-10-28 — `documents_079` retired as a train/eval overlap (owner) by rewording the train side
  (`scripts/gen_train.py`); the eval row is unchanged.
- 2026-10-28 — floors for the feature rows' tags, written from the re-lock that first measured
  them (owner): at the 4B's score in each skill's bar, at the 1.7B's own score under its model
  entry. ffmpeg as rates (`url_input` 0.93 / 0.91, `alerts_and_folders` 0.96 / 0.63,
  `many_files` 0.90 / 0.82), documents as failure budgets (1 / 2, 1 / 8, 1 / 6). The 1.7B mostly
  drops the "notify me when done" part; neither shipped model trained on these rows.
- 2026-10-28 — owner exception for `knaif-qwen3-1.7b-v2`: its own lines lowered where the feature
  rows pulled it under an existing bar — documents aggregate 0.909, `extract` 2 and `clarify` 6
  failures; ffmpeg `batch` 0.827. On the kept rows it improved on both skills. The 4B's bars are
  unchanged. Reasons per line in each `acceptance.yaml`.
- 2026-10-29 — "make it smaller" checks its result (owner, from the manual test: a `.mov` came out
  of `compress_video` bigger than it went in). Both runtimes: the audio is never re-encoded above
  the source's bitrate (copied when it is already the codec the output wants); a compress that is
  not smaller writes nothing and says so, or, for a chain's intermediate, delivers it as it was
  (the encode, if the intermediate is another format, so a conversion asked for is not lost);
  one that is smaller says by how much ("N% smaller (A → B)"). `compress_pdf` prints the same
  line. A `target_size_mb` the request never states is left out of the plan (`stated_args`, a new
  `tools.yaml` field, gated like `grounded_args`). New fs toolkit tool `stage_copy`. Three
  `compress_result` rows join `eval.jsonl` (ffmpeg 378 rows); their floor is a row budget,
  `max_failures: 1`, from the re-lock that first measured them (4B 8/9, 1.7B 9/9). User-facing
  line: *"Make it smaller" never hands back a bigger file: it says how much it saved, or that it
  could not and left the file as it was.*
